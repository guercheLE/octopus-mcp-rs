# Documentation gaps and lessons learned

This repo does not have a full PRD/architecture doc set. Its `docs/` folder holds
only three files: [`SCHEMA_VERSIONS.md`](SCHEMA_VERSIONS.md) (a one-table mapping
of API version → OpenAPI source → store file → schema file), the embedded
[`octopus-openapi-v2023.4.8290-3.1.json`](octopus-openapi-v2023.4.8290-3.1.json)
spec itself, and [`mcp-prompts-workflow-plan.md`](mcp-prompts-workflow-plan.md) (a
detailed design doc, but scoped to a single feature — the MCP prompts layer — not
the whole system). The [README](../README.md) covers usage, configuration,
observability, and credential storage, but is not a planning document; it describes
the system as it currently is, not the decisions and constraints behind it.

That narrower baseline only changes *which* docs each gap below is compared
against — it does not narrow how the history was mined. Every commit across all
34 tagged releases (`v0.1.1` through `v0.7.8`, ~78 commits total) was walked to
find every `fix:` commit implying a real design/doc gap and every `feat:` commit
retrofitting something a planning doc should have anticipated.

This repo is generated by a separate tool, **mcpify**
(`/Users/lucianoguerche/Documents/GitHub/mcpify`), from shared Rust code-generation
templates. A striking pattern falls out of the full history: the large majority of
non-trivial `fix:` commits here are not Octopus-Deploy-domain bugs at all — they're
bugs in generic, generated infrastructure (auth-credential cascade, embedded-store
extraction, stdio transport, CI/release workflow, schema `$ref` handling) that this
repo's own commit messages frequently cross-reference as also found in sibling
repos (`bamboo-mcp-rs`, `spotify-mcp-rs`) or fixed upstream in mcpify itself. Those
are tagged **(shared mcpify-template gap)** below — they're the highest-leverage
findings for improving docs across the whole fleet, not just this repo. Entries
tagged **(repo-specific)** are genuine gaps in *this* repo's own domain docs.

For every `(shared mcpify-template gap)` entry, the **Doc gap** section below
was re-grounded directly against mcpify's own planning docs
(`/Users/lucianoguerche/Documents/GitHub/mcpify/docs/product-brief.md`, `prd.md`,
`architecture.md`, and the versioned `vN-implementation-plan.md` files) rather
than just noting that this repo's own local docs don't cover it — it states
specifically what mcpify's PRD/architecture *should have specified* but didn't,
since that's the actual root cause that then required a fix here (and, per that
commit's own words, in one or more sibling repos too). Where mcpify's own
`docs/DOC-GAPS.md` and `CHANGELOG.md` already document the same root cause
(they were written independently, using the identical git-history-mining
methodology, against mcpify's own commit history), this file points there by
name instead of re-deriving a differently-worded version of the same finding.
Three entries below turned out to have **no** matching root-cause writeup in
mcpify's own `docs/DOC-GAPS.md` even though the fix demonstrably shipped there
too (confirmed via mcpify's own `git log`/`CHANGELOG.md`) — those are flagged
inline as **new findings**, worth a fresh entry in mcpify's own gap doc.

## Lessons for future docs

1. **Write a "platform support & known OS-specific behavior" section before
   shipping CI for any Rust project bundling native/platform-sensitive
   dependencies** (an ONNX Runtime / embedding model, a TLS backend like `rustls`,
   stdio/console transports). Five separate Windows-only bugs
   (§ 2026-07-16→07-19 below) and one cross-platform ONNX Runtime build breakage
   (§ 2026-07-10) all trace back to nobody having written down, up front, which
   OS/runtime behaviors the design was implicitly assuming were universal (POSIX
   rename semantics, POSIX EOF-on-closed-stdin semantics, glibc symbol
   availability, a specific OS's prebuilt-binary availability).
2. **In a generated/scaffolded repo, explicitly document the generated-vs-hand-authored
   boundary, and keep a running "upstream-worthy fixes" list.** Every hand-patch
   applied directly to a generated file is silently at risk of being dropped by
   the next resync — and multiple fixes in this repo's history *were* dropped and
   had to be re-applied (§ 2026-07-18/19 below) before finally landing upstream in
   mcpify itself. A planning doc for any generated repo should say, in one place,
   "these N files/behaviors are hand-patched ahead of the generator; re-verify
   after every `mcpify sync`."
3. **Document concurrency/lifecycle invariants for shared or cached resources as a
   testable contract, not a comment.** `resolve_store_path`'s docstring already
   *claimed* extraction happened once per process before that was actually true
   (§ 2026-07-16→07-19) — a planning doc should pair the stated invariant with the
   specific test that proves it, since the gap between "documented intent" and
   "actual behavior" is exactly where these bugs lived.
4. **For any tool that facades a third-party OpenAPI spec, document the fallback
   contract for when the upstream spec is wrong** (mismatched response shape,
   dangling `$ref`, additionalProperties too narrow) as a first-class, explicit
   behavior — warn-and-return vs. reject — decided at design time. This project
   discovered the need for that contract via a bug report (§ 2026-07-16), and
   confirmed the same class of upstream-spec bug independently in Atlassian's Jira
   Data Center spec and in Octopus's own spec's dangling `$ref`s (§ 2026-07-26).
5. **State CI/release operational budgets up front**: expected job duration per
   platform, and an explicit `timeout-minutes` policy, rather than relying on
   GitHub Actions' 6-hour default ceiling as the only safety net. This repo only
   added timeouts after a sibling repo's incident actually burned hours of CI time
   (§ 2026-07-21).
6. **Maintain a "shared template surface" checklist in the planning doc for any
   repo that is one of a generated fleet** — auth/credential cascade, embedded-store
   extraction, CI build/release workflow, schema `$ref` handling, logging/redaction.
   When a bug is found in one sibling repo, check it against this list and the rest
   of the fleet immediately, rather than rediscovering it independently in each
   repo months apart (as happened here at least three times — see the OAuth
   cascade, mutex-poisoning, and multi-arch GHCR entries below).
7. **Do the "full operation-catalog re-scan for coverage" pass during initial
   design, not after shipping v1.** The MCP prompts feature's first release
   covered 10 domains; a deliberate second pass over the *entire* operation
   catalog (§ 2026-07-20, round 2) found three whole domains — interruptions,
   Config As Code, server administration — with real, actionable operations and
   zero prompt coverage. That re-scan technique should be a mandatory design step,
   not an afterthought triggered by a gap being noticed in practice.
8. **Settle naming conventions before implementation, not via a post-ship rename.**
   The MCP prompt names shipped in v0.6.0/v0.7.0 and were renamed in v0.7.1 purely
   for naming-convention consistency (§ 2026-07-20) — a one-paragraph "naming
   conventions" section in the original plan doc would have caught this before
   any client integrated against the old names.
9. **A requirement that names a mechanism ("emit an auth-strategy module," "attach
   the required header/query/basic credentials") must also name the *source of
   truth* for that mechanism's variable parts.** mcpify's own `prd.md` REQ-1.2.2
   and `architecture.md`'s "Credential injection" step both describe attaching
   an auth header without ever stating the header name must come from the
   scheme's own declared name (`AuthSchemeDescriptor`) rather than a per-scheme
   hardcoded default (§ 2026-07-15 below). The lesson generalizes: whenever a
   planning doc says a generator "reads X from the spec," it should also say
   *which spec field* feeds every generated literal that varies per-API, not
   just the ones that were top-of-mind while writing the requirement.
10. **When a fix is confirmed to also exist in the generator or a sibling repo,
    check the generator's own gap-analysis doc before assuming the root cause is
    already written down there — its absence is itself a finding.** Cross-checking
    every `(shared mcpify-template gap)` entry below against mcpify's own
    `docs/DOC-GAPS.md` found several fixes that shipped in mcpify's own history
    (confirmed via its `CHANGELOG.md`/`git log`) but were never given a
    root-cause writeup there — meaning the "doc gap → fix" loop closed at the
    code level but not at the documentation level, even in the one repo whose
    explicit job is generating documentation-complete projects.

## Dated entries

### 2026-07-26 (v0.7.7, v0.7.8) — multi-arch GHCR image never actually multi-arch (shared mcpify-template gap)

#### Doc gap
No doc (README's Docker section or otherwise) specified that the GHCR image
publish step must set `platforms:` explicitly, or that QEMU-emulated cross-builds
are unreliable enough to avoid for a multi-arch matrix. The release workflow ran
`docker/setup-buildx-action` but never passed `platforms:` to
`docker/build-push-action`, so it silently only ever built `linux/amd64` — arm64
hosts (Apple Silicon, arm64 CI runners) got "no matching manifest" pulling the
published image.

At the root: mcpify's own `docs/prd.md` REQ-2.3.7 ("Packaging & delivery")
requires "a CI/CD pipeline (GitHub Actions) with automated versioning/publishing
... matching the delivery pattern already proven by both reference servers," but
never states an architecture-*coverage* requirement (which CPU architectures the
published image must support) for that pipeline, and never flags that
QEMU-emulated cross-architecture Docker builds are unreliable in CI. That
under-specification is what let every mcpify-generated project's Dockerfile/CI
template ship a single-arch-only image. This is already documented at the root
in mcpify's own `docs/DOC-GAPS.md`, entry "2026-07-26 - multi-arch container
images not specified (v0.11.12 - v0.11.14)" — see that entry rather than
re-deriving it here.

#### Resulting work
v0.7.7 added `platforms: linux/amd64,linux/arm64` with QEMU emulation; v0.7.8
replaced that with Docker's build-by-digest-then-merge pattern (native
`ubuntu-24.04` + `ubuntu-24.04-arm` matrix jobs, merged via
`docker buildx imagetools create`) once QEMU alone proved insufficient. This
exact same two-step fix — QEMU-emulated multi-arch first (mcpify v0.11.12), then
native-runner build-by-digest (mcpify v0.11.14) — shipped in mcpify's own
repository under the identical commit wording, confirming the release-workflow
template itself was the root cause, not anything Octopus-specific.

### 2026-07-21 → 2026-07-26 (v0.7.4, v0.7.6) — stored schemas never fully resolved their `$ref`s (shared mcpify-template gap)

#### Doc gap
`SCHEMA_VERSIONS.md` documents which file holds which store/schema artifact, but
says nothing about the *resolution guarantee* callers can expect from a schema
`get` returns — i.e., that it will be self-contained rather than referencing a
`$defs` block the caller has to resolve itself. That contract was never written
down, so two separate passes were needed before it actually held.

At the root: mcpify's own `v1-implementation-plan.md` made a deliberate,
documented decision to embed a full standalone copy of the component-schema
library into every operation's schemas — reasoned as "simpler and more robust
than cross-schema `$ref` resolution, at the cost of some file size" — but that
cost/correctness trade-off was never bounded or re-checked against real specs.
`prd.md` REQ-2.4.1 and `architecture.md`'s "Data Layer" section both call
`mcp_store.db` "self-contained" without ever specifying what self-contained
schema output should mean at scale (reachable-only vs. whole-library, inlined
`$ref` vs. localized `$defs`). This is already documented at the root in
mcpify's own `docs/DOC-GAPS.md`, entry "2026-07-21 to 2026-07-26 -
self-contained schema/`$ref` handling took three iterations (v0.5.12, v0.11.5,
v0.11.7)" — see that entry for the full three-iteration history. This repo's
own commits only show the second and third of those three iterations (v0.7.4 ≈
mcpify v0.11.5, v0.7.6 ≈ mcpify v0.11.7); the first iteration (mcpify v0.5.12,
"embed only reachable schema definitions") appears to have already been folded
silently into an earlier resync in this repo's history rather than showing up
as its own dedicated fix commit here.

#### Resulting work
v0.7.4 regenerated the store/schemas (via `mcpify add-version --set-default --force`,
mcpify 0.11.5) so a `$ref` could no longer point at nothing in a returned `get`
snippet, but still left `$ref`s pointing at a locally-embedded `$defs` map. v0.7.6
recursively inlined every `$ref` that isn't part of a genuine reference cycle,
matching a companion fix landed in the mcpify generator itself. The remaining
un-inlined refs were confirmed to be either a real cycle (`ActivityLogTreeNode`
nesting itself) or dangling references to components that don't exist anywhere in
Octopus's own published OpenAPI spec — a genuine upstream spec bug, and the one
piece of this whole entry that's actually Octopus-domain-specific rather than
generator-level.

### 2026-07-21 (v0.7.3) — no documented CI/release timeout policy (shared mcpify-template gap)

#### Doc gap
No doc covers this at all: neither `release.yml`'s build job nor `ci.yml`'s test
job had a `timeout-minutes`, so a hang in either would fall back to GitHub
Actions' own 6-hour job ceiling as the only bound.

At the root: mcpify's own `docs/prd.md` REQ-2.3.7 ("Packaging & delivery")
requires "a CI/CD pipeline (GitHub Actions) with automated versioning/publishing"
but says nothing about job-level operational budgets — confirmed by grepping
`prd.md` and `architecture.md` for "timeout": zero matches in either file.
**This is a new finding, not yet covered in mcpify's own `docs/DOC-GAPS.md`**:
mcpify shipped the identical fix in its own repository — `fix(rust): cap the
release workflow's build job at 45 minutes` (mcpify commit `adf0b3c`, released
as v0.11.3) and `fix(rust): cap the CI test job at 20 minutes` (mcpify commit
`21f4e96`, v0.11.4), both dated 2026-07-21, both explicitly citing the same
`bamboo-mcp-rs` incident cited below — but neither mcpify's `docs/DOC-GAPS.md`
nor `docs/prd.md` was ever updated with a "CI/CD pipelines must declare a
timeout budget" requirement. Worth adding there.

#### Resulting work
Added `timeout-minutes: 45` to `release.yml`'s build job (normal completion under
20 minutes) and `timeout-minutes: 20` to `ci.yml`'s test job. This was prompted
directly by a real incident in the sibling `bamboo-mcp-rs` repo, where an
un-timed job hit exactly this ceiling after a hang caused by the same
mutex-poisoning bug fixed the same day (below) — the only thing that had actually
bounded that incident was GitHub's own hard ceiling.

### 2026-07-21 (v0.7.2) — no documented lock-poisoning recovery contract for the shared store connection (shared mcpify-template gap)

#### Doc gap
No doc specifies what should happen to the process-wide cached store connection
if a panic occurs while its lock is held. The implicit assumption — that a panic
under this lock either can't happen or should propagate — was never stated or
tested, and was wrong: since all access through this lock is read-only, poisoning
should always be recovered from, not propagated.

At the root: mcpify's own `architecture.md` §"Data Layer" describes
`mcp_store.db` extraction and the per-version store cache without ever
mentioning concurrency or lock-poisoning semantics for the shared connection.
This is already documented at the root in mcpify's own `docs/DOC-GAPS.md`,
entry "2026-07-19 to 2026-07-26 - Windows-specific file-locking/timing
semantics unaddressed for the embedded store (v0.10.5 - v0.11.11)" — this
repo's fix corresponds to that entry's `v0.11.2` line
(`fix(rust): recover from mutex poisoning on the shared mcp_store.db
connection`) — see that entry rather than re-deriving it here.

#### Resulting work
Every lock site around `cached_store_connection` now recovers from poisoning
instead of propagating it, and the MCP protocol test gained a 30-second timeout
so a future hang fails fast. The commit message explicitly identifies this as
"the same bug found and fixed in `bamboo-mcp-rs` and in mcpify's Rust
code-generator template" — on `bamboo-mcp-rs`'s CI this exact bug turned one
flaky test failure into the next test hanging for hours.

### 2026-07-20 (v0.7.1) — no naming convention documented for MCP prompt identifiers (repo-specific)

#### Doc gap
`mcp-prompts-workflow-plan.md` specifies the full prompt inventory, argument
shapes, content-design pattern, and sequencing for the MCP prompts feature in
exhaustive detail — but never states a naming convention for the prompt
identifiers themselves. Prompts shipped as `octopus_workflow[_domain]` in v0.6.0
and v0.7.0.

#### Resulting work
v0.7.1 renamed every prompt to the hyphenated, workflow-free form
`octopus[-domain]` (e.g. `octopus-release-deployment`) purely for consistency with
idiomatic MCP identifiers, and updated the plan doc's inventory table and code
snippets to match — a rename that touched already-shipped, externally-visible
names because the convention wasn't settled before the first release.

### 2026-07-20 (v0.6.0, v0.7.0) — flat tool surface left all workflow sequencing undocumented, and the first coverage pass wasn't exhaustive (repo-specific)

#### Doc gap
Neither `SCHEMA_VERSIONS.md` nor the README's original scope ever addressed that
a flat `search`/`get`/`call` surface leaves all multi-step sequencing knowledge —
"to deploy a release you need a project, resolved channel and package versions,
a target environment, and (if tenanted) a tenant with a connection and required
variables set, in that order" — entirely up to whichever LLM is driving the
client, re-derived from scratch every session. No design doc existed for this
until `mcp-prompts-workflow-plan.md` was written specifically to close it.

#### Resulting work
v0.6.0 shipped an MCP **prompts** capability — a master `octopus` menu plus 10
guided sub-workflow prompts — designed and documented in
`mcp-prompts-workflow-plan.md` before implementation. v0.7.0 then found that the
initial 10-domain breakdown, despite the thorough plan, still wasn't exhaustive:
a deliberate second pass scripted a scan of the OpenAPI spec's `paths` grouped by
path segment and diffed it against actual prompt coverage, surfacing three whole
domains with real, actionable operations and zero coverage — interruptions
(take-responsibility/submit-response actions), Config As Code (a distinct
git-backed persistence model), and a cluster of server-wide admin operations.

### 2026-07-19 (v0.5.9, v0.5.10, v0.5.11) — no documented CI performance budget (shared mcpify-template gap)

#### Doc gap
No doc records an expected per-platform CI job duration or flags Windows as the
outlier — so a large, measurable regression (Windows CI taking roughly 2–2.7x
longer than Linux/macOS for identical work) had to be independently discovered
and profiled rather than checked against a documented baseline. As with the
timeout-policy gap above, neither `prd.md` nor `architecture.md` says anything
about CI performance budgets at all.

The `cargo-dist`-prebuilt-binary half of this is confirmed shared: mcpify's own
`CHANGELOG.md` v0.11.1 records "CI now installs `cargo-dist` from a prebuilt
binary instead of compiling it from source, speeding up release builds" —
matching this repo's v0.5.9 fix. The Windows-Defender-exclusion half is *not*
confirmed shared, and is worth being precise about rather than over-claiming:
grepping mcpify's own repository turns up no CI-workflow change excluding
Defender scanning paths, only a code comment in
`src/targets/rust/templates/data/store.rs.tera` (part of the later
`v0.11.8`–`v0.11.11` Windows-disk-lock-test saga, dated 2026-07-26 — a week
*after* this repo's 2026-07-19 Defender experiment) speculating that "Defender
or a similar background scanner holding an exclusive handle" might explain a
*different*, still-only-partially-resolved flaky-test symptom. Two independent
near-misses at the same suspect, for two different problems, that neither
repo's docs currently connect to each other — worth flagging in mcpify's own
`docs/DOC-GAPS.md` Windows-locking entry (below) as a lead worth following up,
not asserting as an already-confirmed shared fix.

#### Resulting work
v0.5.9 switched `cargo-dist` installation in CI from source compilation to its
prebuilt-binary installer (7m08s → ~8s on Windows). v0.5.10 additionally excluded
the cargo registry and checkout directory from Windows Defender real-time
scanning; v0.5.11 reverted that specific exclusion once measurement showed the
residual gain (19m56s vs 21m41s) didn't justify the added, locally-unvalidatable
risk.

### 2026-07-16 → 2026-07-19 (v0.4.3, v0.5.2, v0.5.8) — embedded-store extraction was never actually safe under concurrency (shared mcpify-template gap)

#### Doc gap
`resolve_store_path`'s own docstring claimed extraction happened once per process
— but no doc (and, for a long time, no test) verified that claim was true under
real concurrent access, either from multiple tokio tasks within one process or
from multiple separate OS processes on Windows.

At the root: mcpify's own `architecture.md` §"Data Layer" describes
`mcp_store.db` extraction and the per-version store cache without ever
mentioning concurrency or platform-specific file-handle semantics — nothing
states that store extraction/rename must be safe under concurrent calls, or
that Windows releases file handles on a different timeline than POSIX. This is
already documented at the root in mcpify's own `docs/DOC-GAPS.md`, entry
"2026-07-19 to 2026-07-26 - Windows-specific file-locking/timing semantics
unaddressed for the embedded store (v0.10.5 - v0.11.11)," which lists at least
nine separate fixes needed before this stabilized in mcpify itself — see that
entry rather than re-deriving it here. This repo's three fixes map directly
onto three of those: v0.4.3 (atomic extraction) ≈ mcpify v0.8.2, v0.5.2
(per-process cache) ≈ mcpify v0.10.5, v0.5.8 (cross-process rename retry) ≈
mcpify v0.11.1.

#### Resulting work
Three separate hardening passes were needed against the same code path:
v0.4.3 made the extraction write atomic (write-to-sibling-then-rename) after
concurrent tool calls hit spurious "no such table" errors reading a
mid-truncate file; v0.5.2 added a per-API-version cache behind a mutex so
extraction genuinely happens once per process, after a Windows-only rename race
was surfacing as unrelated MCP-protocol test failures in CI; v0.5.8 added a
retry-with-backoff around the rename itself after discovering the in-process
cache couldn't stop a *different OS process* from having the destination file
open at the exact moment of rename — explicitly noted as fixing "the same latent
race for real concurrent Windows deployments, not just this test suite." This is
the embedded-store extraction mechanism every mcpify Rust target shares, not
anything Octopus-specific.

### 2026-07-19 (v0.5.4, v0.5.5, v0.5.7) — Windows console/stdio EOF handling never validated against generated transport/CLI code (shared mcpify-template gap)

#### Doc gap
No doc noted that Windows' handling of a closed/non-console stdin fundamentally
differs from POSIX for both the `rmcp` stdio transport and the `inquire`-driven
interactive `setup` wizard — both generated code paths implicitly assumed POSIX
EOF semantics. The two closest mcpify sections — `prd.md` REQ-1.6 ("Guided
Setup Wizard," which only addresses *where* collected values persist, never how
input is read) and `architecture.md`'s "Dual-Role Execution" section (which
picks `stdio` vs. `http` transport but never connects that choice to
platform-specific console/stdin behavior) — are both silent on this.

**This is a new finding, not yet covered in mcpify's own `docs/DOC-GAPS.md`.**
The fix demonstrably shipped in mcpify's own repository under near-identical
commit messages — `fix(rust): stop the stdio smoke test from hanging on
GitHub Actions Windows` (mcpify commit `1945201`) and `fix(rust): stop the
setup smoke test from hanging on GitHub Actions Windows` (mcpify commit
`0acf63f`), both reflected in mcpify's `CHANGELOG.md` as v0.10.7/v0.10.8 and
the related v0.10.1 TTY fix — but mcpify's own `docs/DOC-GAPS.md` has no
root-cause entry for it. Note this is a *distinct* root cause from the
store-extraction concurrency gap above (console/stdin EOF semantics vs.
file-rename/lock semantics), even though both surfaced the same week and both
are Windows-only — worth its own fresh entry in mcpify's gap doc rather than
being folded into the existing Windows-locking one.

#### Resulting work
v0.5.4 first just relaxed a test assertion that checked exact `rmcp` error text
(Windows doesn't surface the same wording). v0.5.5 found the deeper problem: on
GitHub Actions Windows runners the stdio smoke test didn't just get different
text, it hung indefinitely (previously manually cancelled after ~5 hours) because
Windows' background blocking-thread stdin reader never observes an
immediately-EOF-closed child stdin the way Unix does. v0.5.7 found the identical
root cause at a second call site — the `setup` wizard's `inquire` prompts read raw
console input on Windows rather than treating closed stdin as EOF — causing the
same multi-hour hang once the v0.5.5 fix let test execution reach that far. Both
hangs were worked around with a runtime check scoped specifically to
`GITHUB_ACTIONS`, not a blanket Windows skip, so real Windows developers still get
full coverage.

### 2026-07-19 (v0.5.0, commit `7bc5ce8`) — hand-patched fixes were silently dropped by the generator on resync (shared mcpify-template gap)

#### Doc gap
No doc recorded which parts of this repo were hand-patched ahead of mcpify's own
generator, so there was nothing to check before each resync — and real,
previously-fixed content was in fact silently lost and had to be re-discovered.

At the root: mcpify's own `prd.md` REQ-2.5.1 (zero-placeholder generation) and
`architecture.md`'s directory-guard description ("abort with a warning unless
[the output dir] is empty or `--force` is set") define what a fresh generation
run must produce, but neither says anything about what re-running `generate
--force` over an *already-generated, already-hand-patched* project is allowed
to silently regress. **This is a new finding, not yet covered in mcpify's own
`docs/DOC-GAPS.md`** as its own root-cause entry, even though the fix
demonstrably shipped there: mcpify's `CHANGELOG.md` v0.10.0 records, in nearly
the same words as this repo's own resync commit, "Restored cargo-default
`.gitignore` entries and the `.mcpify` scratch-file guard," "Restored the
Observability & Resilience, License, and install sections to the generated
Rust README (had been dropped)," and "Isolated generated Rust `cli_smoke`
tests... from the developer's real global config" — confirming the
regeneration-can-silently-regress-content problem was real at the generator
level, not just something this repo's own maintenance process mishandled. A
"regeneration/`add-version`/resync must never silently regress previously
shipped, template-covered content" requirement belongs in `architecture.md`
alongside the existing directory-guard description.

#### Resulting work
This single resync commit's own message documents the extent of it: the `.gitignore`
cargo-default entries and `.mcpify/*` scratch-file guard, and the README's
Observability & Resilience / License / install sections, had "previously [been]
hand-authored directly in generated repos and silently dropped by sync's older
thin templates" before finally being fixed upstream in mcpify itself. The same
resync also picked up the api_key auth strategy finally using its real declared
header name (`X-Octopus-ApiKey`) by default instead of the hardcoded value this
repo had been hand-patching around since v0.4.0 (below), and fixed
`tests/cli_smoke.rs` reading the real machine's global config. Every one of these
is evidence of the same underlying gap: nothing tracked the hand-patch/generator
boundary, so fixes only "stuck" once someone happened to notice they'd
regressed.

### 2026-07-16 (v0.4.2) — no documented contract for upstream OpenAPI spec errors (shared mcpify-template gap)

#### Doc gap
No doc stated what the generated `call` tool should do when a live API response

### 2026-07-10 (v0.2.4) — no documented platform/runtime constraints for the embedding-model dependency (shared mcpify-template gap)

#### Doc gap
No doc recorded the actual platform support matrix for the ONNX Runtime (`ort`)
dependency backing the embedded semantic search feature — so three separate,
unrelated platform failures (dropped x64 macOS support upstream, a too-old glibc
on the default Ubuntu CI runner, an incompatible static-vs-dynamic Windows CRT
link mode) all had to be discovered independently via broken release builds
rather than checked against a documented constraint list.

At the root: mcpify's own `docs/project-manifest.md` states, as a fact rather

cargo-dist configuration with the supported ONNX Runtime target matrix" — that
sentence documents *that* a target matrix exists, but not *what it is* or that

what glibc/CRT-linking constraints those binaries carry). This is a *related
but distinct* gap from mcpify's own `docs/DOC-GAPS.md` entry "2026-07-04 -
native/runtime dependency self-containment inconsistent across targets
(v0.1.0 - v0.9.0)," which covers auto-*downloading* a missing native dependency
(C#'s `sqlite-vec`, Go's ONNX Runtime shared library) at run time, not the
separate problem of which **release-build targets** `cargo-dist` can even
produce given `ort`'s own prebuilt-binary constraints. mcpify's `CHANGELOG.md`

#### Resulting work

embedding-cache/semantic-search dependency every mcpify Rust target with search
enabled shares — the specific breakage isn't about Octopus Deploy at all.
